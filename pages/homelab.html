02 / Architecture

Separate networks, clear responsibilities

The design uses VLANs to separate traffic by purpose, with inter-VLAN access denied by default and specific exceptions where needed.

03 / Design decisions

The reasoning behind the setup

01

One source of truth

My infrastructure repository previously contained conflicting network plans because address data was maintained in several places. The current approach defines the network in YAML and generates the host documentation, network tables, and router configuration from it.

Validation checks for overlapping subnets, duplicate addresses, invalid reservations, and mismatched references. CI checks that the generated files match the source data.

Implemented in the infrastructure repo
02

Keep experiments away from household traffic

The design gives management, workloads, trusted devices, IoT, guests, and experiments separate network zones. A default-deny policy makes every exception an explicit decision.

The aim is to make room for testing configurations without making household connectivity depend on an experiment.

Documented design · deployment pending
03

Keep storage traffic close to compute

Storage and compute share a VLAN in the design, allowing backup and object-storage traffic to be switched rather than routed across a trunk twice.

The tradeoff: storage isn't a separate network policy boundary. Access control must also be enforced through service accounts and share permissions.

Documented design · deployment pending

04 / Next steps

From design to a running lab

The network model and configuration generator are in place. The next work is to verify the physical setup and bring it online in stages.

  1. In progress

    Verify the hardware

    Confirm memory, storage, network connections, and device roles against the inventory.

  2. Planned

    Bring up the network

    Finalize DNS, internal TLS, and IPv6 decisions. Stage the router configuration and validate access between zones.

  3. Planned

    Establish core services

    Deploy Proxmox, redundant DNS on separate hosts, remote access, and backups. Test recovery before adding more workloads.

  4. Planned

    Add workloads and monitoring

    Introduce shared object storage and metrics, then document what works with deployment notes and real lab photos.
